1. EXECUTIVE SUMMARY: THE ECONOMICS OF THE CONTEXT WINDOW
--------------------------------------------------------------------------------
Large Language Models (LLMs) operate on context windows measured in "tokens".
In software engineering workflows, token accumulation is exponential, not linear.
Every time you send a message, the entire active conversation history, open editor
tabs, system prompts, and file structures are re-transmitted.

Without proper hygiene, a developer can consume 50,000+ tokens on a single minor
change because they are carrying the weight of past tasks. This guide outlines the
"Stateless Workflow" methodology designed to minimize cost and maximize output.

================================================================================
2. THE GOLDEN RULES OF CONTEXT HYGIENE
================================================================================

[RULE #1] THE PRINCIPLE OF STATELESS SESSIONS (The most critical optimizer)
  * Treat each chat thread as a single-task runner.
  * Once a task (e.g., "build schema migrations" or "add route handler") is done
    and the code compiles successfully, CLOSE the current thread.
  * Start a clean, brand-new chat session for the next task.
  * IMPACT: Reduces token overhead on subsequent prompts by up to 90%.

[RULE #2] DELEGATE FILE READING TO THE AI'S TOOLING
  * Never copy and paste large source code files into the chat interface.
  * If the assistant has access to the workspace, reference the path:
    "Review src/components/admin/ProductTable.tsx and add X..."
  * The assistant will use tools like `view_file` to read only the lines it
    actually needs, drastically reducing initial prompt size.
  * IMPACT: Saves thousands of tokens per prompt.

[RULE #3] CLOSE UNUSED IDE TABS (Scope Minimization)
  * Modern AI assistants dynamically scan your open editor tabs to build context.
  * If you have 15 tabs open (unrelated utilities, old migrations, CSS styles),
    all of them are injected into the background context.
  * Keep ONLY the active files you are working on open in your IDE.
  * IMPACT: Reduces context payload and prevents the AI from getting confused.

================================================================================
3. ELITE PROMPT ENGINEERING ARCHITECTURE
================================================================================
When prompting, write like a Technical Lead writing a Ticket, not a conversationalist.
Structure your prompts with: Context, Task, Constraints, and Output Format.

[BAD PROMPT (High token waste, highly ambiguous):]
  "Hey, so I want to build a page for bulk uploading product details. Can you help
  me do that? Let's check how the current admin stuff is implemented and then
  write a similar feature but with the new columns we discussed earlier. Thanks!"
  --> Consumes tokens on back-and-forth clarification.

[EXCELLENT PROMPT (Highly efficient, high first-turn success rate):]
  "Task: Expand bulk upload to support product details.
   Context:
     - Active endpoint: /api/products/bulk/route.ts
     - Upload Modal: BulkUploadModal in src/components/admin/ProductTable.tsx
   Requirements:
     1. Add optional columns to CSV: 'Long Description', 'Highlights', 'Specifications'.
     2. Parse these in `processFile()` in ProductTable.tsx.
     3. Update API to insert into `product_details` using product_id.
   Constraints:
     - Keep existing database validation.
     - Return strict JSON error responses if required fields are missing."
  --> Achieves success in exactly 1 turn. Saves thousands of iterative tokens.

4. ATOMIC DEV WORKFLOW (STEP-BY-STEP REFACTORING)
================================================================================
Large changes should be segmented into a pipeline. Do not ask the assistant to
implement a complex feature all at once.

Instead, follow this architectural sequence:
  Phase 1: Database Migration & Schema Design (Clear, verify, new thread)
  Phase 2: Backend API Routes & Controllers (Clear, verify, new thread)
  Phase 3: Frontend Component UI Shell (Clear, verify, new thread)
  Phase 4: Client-State Integration & API Hookups (Clear, verify, done)

By closing and starting a new chat thread between phases, you guarantee that:
  - Code is modular.
  - Token consumption is kept strictly localized.
  - The model does not suffer from "attention drift" (forgetting details from
    phase 1 because it's overwhelmed by frontend UI markup).

================================================================================
5. SYSTEMATIC DEBUGGING WITHOUT TOKEN BLEED
================================================================================
When code fails, do not paste the entire 100-line error stack trace repeatedly.

How to debug efficiently:
  1. Paste ONLY the top 3-5 lines of the stack trace (which contain the actual
     exception type, error message, and file name/line number).
  2. Specify the environment (e.g., "Happens during Next.js production build" or
     "Runtime error during client-side hydration").
  3. Tell the assistant which specific file you suspect has the error.

================================================================================
6. INTEGRATING NEW FEATURES INTO AN EXISTING CODEBASE (ARCHITECT'S PLAYBOOK)
================================================================================
Adding features to an existing project has unique challenges. If not managed properly,
the AI can introduce bugs, duplicate code, or break existing functions (regressions).
Follow this step-by-step strategy for maximum token and code efficiency:

STEP 1: THE DISCOVERY PHASE (Don't let the AI guess)
  * Instead of asking the AI to "write X feature", first ask the AI to find 
    existing code patterns:
    * E.g.: "Search the project for existing API endpoints or data schemas to see
      how database queries and roles are structured."
  * This ensures the new feature perfectly aligns with the current architecture
    (e.g., using existing DB libraries, router frameworks, or icon packages).

STEP 2: PRESERVE CODE BASELINES (Zero Regression Principle)
  * Explicitly tell the AI: "Integrate X feature but preserve the existing features
    A, B, and C. Do not refactor or rewrite the original functionality unless 
    strictly necessary."
  * This keeps diffs extremely narrow and prevents code bloat.

STEP 3: IDENTIFY REUSABLE COMPONENT ASSETS First
  * Existing projects have atomic design tokens, buttons, UI utilities, and styles
    already developed. 
  * Instruct the AI to use existing components: 
    * E.g.: "Use the existing Atoms like Button or custom input fields rather than
      creating new custom styles."
  * This ensures perfect visual consistency and cuts down thousands of lines of
    redundant CSS/TSX code (saving token volume).

STEP 4: ISOLATE THE IMPACT AREA
  * Limit the files the AI modifies. If a new feature can be added in a single new
    file (e.g., a new component or custom hook), do that, rather than adding 
    hundreds of lines of inline code directly to an already bloated parent file.
  * Keep logic separate, then import it!
